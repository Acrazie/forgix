# Release CI sur tag avec git-cliff

## Mandat et statut

Conception du remplacement de Release Please et de la publication locale par une release GitHub Actions déclenchée sur tag, inspirée de CLINT. L'utilisateur a retenu la couverture npm et plugins, leur publication indépendante, et npm Trusted Publishing OIDC. Un seul document de conception est maintenu ici ; aucune implémentation, installation, configuration de compte, opération Git de livraison ou publication n'est autorisée par ce mandat.

Le présent contenu est une proposition soumise à approbation finale, pas une modification déjà réalisée. La revue indépendante couvre architecture, migration, reprise, sécurité et autorisation des publications.

## Contrats retenus

Les identités restent celles du programme existant, sans renommer les paquets ni forcer la synchronisation de toutes les releases :

| Cible         | Tag stable exact        | Contrat de version au SHA tagué                                                           | Effets CI                   |
| ------------- | ----------------------- | ----------------------------------------------------------------------------------------- | --------------------------- |
| npm + plugins | `vX.Y.Z`                | npm, Claude, Antigravity et entrée marketplace Forgix à `X.Y.Z` ; Codex à `X.Y.Z+codex.T` | npm, GitHub Release, miroir |
| npm seul      | `npm-vX.Y.Z`            | npm à `X.Y.Z` ; versions plugins conservées                                               | npm, GitHub Release, miroir |
| plugins seuls | `plugin-vX.Y.Z-codex.T` | base plugins et marketplace à `X.Y.Z` ; Codex à `X.Y.Z+codex.T` ; version npm conservée   | GitHub Release uniquement   |

`X.Y.Z` utilise les entiers SemVer stables sans zéro initial ; `T` est un horodatage UTC valide de 14 chiffres. Pas de prerelease dans cette migration. Pour plugins seuls, conserver le comportement existant : changement du cachebuster Codex, pas de nouvelle base Claude/Antigravity. Cela ne promet pas une notification de mise à jour identique dans tous les hôtes.

Un tag constitue une demande explicite de publication par un mainteneur autorisé. La CI ne choisit ni ne réécrit la version. Le push du tag intervient seulement après fusion de la préparation par PR et validation du SHA exact sur `main`. Aucun push direct de commit sur `main` par l'outil ou la CI. La CI ne crée, ne déplace et ne supprime aucun tag. Les anciens tags `forgix-v*` et autres noms historiques restent consultables, mais ne déclenchent pas la nouvelle publication ; ne pas les republier automatiquement.

## Préparation et propriété des changements

Conserver `bun run release` comme entrée de préparation locale uniquement, en remplaçant clairement ses anciens choix de publication/reprise. Sur une branche de travail propre, l'outil réutilise les validations et calculs de version pertinents de `release-lib.ts`, prépare les fichiers, affiche cible, versions, tag attendu et notes, puis s'arrête. Il ne commit, ne pousse, ne crée de PR/tag/release, ne publie et n'installe aucun plugin. Le mode preview ne laisse aucune modification durable. L'ancienne option `--publish-existing` refuse avec une consigne de reprise CI ; elle ne conserve pas une voie locale de publication concurrente.

Pour npm, le mainteneur garde le choix final d'une version stable supérieure ; le calcul existant reste une recommandation, corrigée pour utiliser l'historique du plan npm plutôt que le dernier tag quelconque. Pas de deuxième moteur SemVer git-cliff dans cette migration. Pour plugins, réutiliser le cachebuster UTC et la validation multi-harness ; pour `both`, aligner les bases comme aujourd'hui.

Préparer métadonnées ciblées, `bun.lock` si nécessaire, bundle déterministe et changelog dans la même PR. Les versions hors cible restent inchangées ; le bundle livré aux plugins doit refléter le source même pour une release plugins seuls. La CI compare le bundle reconstruit aux octets suivis dans le commit, sans corriger le dépôt. Toute dérive bloque et nécessite une nouvelle préparation.

Créer un `cliff.toml` racine propre à Acrazie/forgix : Conventional Commits, liens vers commits/PR Forgix, breaking changes toujours conservés, regroupement lisible, exclusion des commits purement `chore(release)`. Ne pas copier les exclusions CLINT qui pourraient masquer un breaking change. Pas d'enrichissement contributeurs nécessitant un token en préparation locale. Épingler une version git-cliff et la même configuration pour préparation et CI ; une mise à jour d'outil est séparée de la release.

Le fichier `plugins/forgix/CHANGELOG.md` reste canonique. Conserver son historique existant sans réécriture des anciennes sections/liens. Ajouter une section par nouvelle identité exacte, y compris plugins seuls. La préparation produit le texte avec git-cliff et une plage explicite ; après fusion, CI régénère la section et vérifie son équivalence, hors commit de préparation filtré. Pas de commit changelog après le tag. Date déterministe : date UTC persistée dans la section de préparation, jamais l'heure d'une relance.

Pour éviter qu'un tag plugins masque des changements npm, distinguer deux historiques : plan npm (`v*`, `npm-v*`), plan plugins (`v*`, `plugin-v*`). La borne précédente est le dernier tag ancêtre admissible du même plan, par ordre topologique sur l'historique de `main`, pas la plus grande version ni la date de création. `both` produit deux sous-sections à partir de ces deux plages, en dédupliquant les plages identiques ; `npm` ou `plugin` n'utilise que son plan. Chaque sous-section nomme sa borne. Plusieurs tags admissibles au même commit doivent être désambiguïsés par une règle testée privilégiant `v*` ; un conflit de versions bloque. À la transition, inventorier les tags distants historiques et enregistrer dans la configuration les seules correspondances historiques nécessaires après vérification, sans inventer de nouveaux tags. En l'absence de borne, partir du début de l'historique et l'afficher explicitement. Une section déjà présente pour la même identité ne peut pas être ajoutée deux fois.

## Pipeline cible et frontières de confiance

Créer `.github/workflows/release.yml`, déclenché sur les trois familles de tags et par `workflow_dispatch` avec un tag existant pour reprise. Le filtre de déclenchement n'est pas une validation : le premier job applique les formats exacts. Le workflow doit être présent sur `main` pour permettre le dispatch. Toute exécution de release, push ou dispatch, doit toutefois s'exécuter dans le contexte de la référence tag exacte : pour le dispatch, sélectionner ce tag comme référence d'exécution et fournir le même tag en entrée. Exiger `github.ref == refs/tags/<tag>` et `github.sha == SHA résolu`, puis vérifier l'intégration du commit à `main`. Un dispatch depuis la branche `main` est refusé, même avec un checkout du bon tag : le checkout ne corrige pas le contexte source des attestations. La définition privilégiée provient ainsi du commit tagué intégré à `main`. Ne jamais falsifier `GITHUB_SHA` pour faire correspondre une attestation.

1. **Résoudre et autoriser**, sans permission d'écriture : vérifier dépôt `Acrazie/forgix`, événement et référence du workflow ; récupérer l'historique et les tags, résoudre `refs/tags/<tag>^{commit}` en SHA, exiger l'appartenance de ce SHA à `origin/main`. Entrée tag transmise comme donnée, jamais interpolée dans un script shell. Refuser tag absent, mal formé, manifeste discordant, identité déjà attribuée à un autre SHA ou référence d'exécution différente du tag, y compris la branche `main`. Le tag doit être créé par un acteur déjà autorisé par les contrôles GitHub du dépôt ; ne pas ajouter de PAT ni élargir les droits. La protection effective des tags doit être vérifiée avant activation, pas déduite de la protection de `main`.
2. **Valider et construire**, sans secret de publication : checkout du SHA exact, `persist-credentials: false`, outils épinglés, installation Bun frozen. Exécuter l'équivalent complet des lanes CI actuelles sur ce SHA, y compris Ubuntu/macOS et tests release ; réutiliser les commandes existantes, pas seulement un statut vert de la tête courante de `main`. Valider tous les manifests, les invariants de cible, bundle, changelog et notes. Les CLI hôtes facultatives restent des vérifications supplémentaires quand disponibles ; la validation locale de schéma n'en dépend pas.
3. **Préparer le candidat npm**, seulement pour une cible npm : après validations, `npm pack --ignore-scripts` dans `plugins/forgix`, inspection de la liste des fichiers et du paquet extrait, test runtime du tarball exact sur plateformes supportées. Le pack n'exécute pas `prepublishOnly` : ses checks doivent donc avoir été exécutés explicitement. Enregistrer SHA source, tag, cible, versions, SHA-512 du tarball et notes dans un artefact Actions immuable du run. Utiliser le même tarball testé pour publier ; aucun rebuild dans le job privilégié.
4. **Publier npm**, seulement pour une cible npm : runner GitHub hébergé, environnement protégé `release`, `contents: read`, `id-token: write`, aucun secret npm ni `NODE_AUTH_TOKEN` npmjs. Télécharger uniquement l'artefact du run validé ; vérifier son identité et son digest avant `npm publish <tarball> --ignore-scripts --access public --registry=https://registry.npmjs.org`. Ne pas installer les dépendances projet ni exécuter du code projet dans ce job ; seulement les vérifications et CLI de publication auditées. Après publication, vérifier nom, version, intégrité et attestation automatique de provenance npm : celle-ci doit désigner le dépôt Forgix, le SHA exact et le digest du tarball validé. Ces preuves sont obligatoires dans le mode public retenu ci-dessous. Si une vérification échoue après acceptation npm, signaler une release partielle et investiguer, sans republier ou unpublish. Une erreur réseau/authentification n'est jamais assimilée à une absence de version.
5. **Publier GitHub Release**, après npm vérifié ou directement après validation pour plugins seuls : seul ce job dispose de `contents: write`. Vérifier à nouveau le tag distant et son SHA, puis créer la release avec notes git-cliff validées et `--verify-tag`. Une release existante doit être stable, non draft, rattachée à la même identité et au même commit ; ne pas écraser une release incompatible. Les plugins restent distribués depuis les manifests et le bundle présents dans Git, sans publication sur un store ni installation personnelle en CI.
6. **Miroir GitHub Packages**, après succès npm et GitHub pour les cibles npm : appeler explicitement le workflow miroir existant, adapté en workflow réutilisable avec `workflow_call`, avec la version stable exacte, jamais `all`. Conserver son entrée manuelle pour récupération. Retirer son déclencheur `release: published` devenu redondant ; un événement produit par `GITHUB_TOKEN` ne garantit pas un nouveau run. `packages: write` est accordé uniquement au job miroir, avec `contents: read`, sans OIDC npm. Réutiliser script et validations de l'alias, sans reconstruire depuis les sources.

Permissions par job, `contents: read` par défaut ; pas de `pull_request_target`, `issues: write`, `pull-requests: write` ou token personnel. Les PR continuent d'exécuter une CI non privilégiée. Actions épinglées au SHA ; pas de cache modifiable par une contribution non fiable dans les jobs publication. Source, notes et candidat restent liés au même SHA. Les privilèges ne transitent pas par les tests ni leurs scripts.

## Authentification et concurrence

Configurer séparément sur npmjs le trusted publisher du paquet existant `@acrasie/forgix` : utilisateur `Acrazie`, dépôt `forgix`, workflow `release.yml`, autorisation de publication directe `npm publish`. Amendement de sécurité approuvé par l'utilisateur pendant l'implémentation : le job npm utilise obligatoirement l'environnement GitHub protégé `release`, et le trusted publisher npm est lié à ce même nom. Avant activation, configurer les règles de déploiement de cet environnement pour autoriser uniquement les familles de tags de release protégés avec des règles de type `tag`, pas `branch` ; aucune branche, même `main`, n'est autorisée. La simple déclaration d'un environnement, qui peut être créé automatiquement sans protection, ne suffit pas. Vérifier séparément sa configuration et les droits de modification des règles avant tout tag de publication. Cette frontière empêche un workflow modifié puis dispatché depuis une branche non intégrée de contourner ses propres contrôles de source et d'obtenir l'autorité npm OIDC. Aucune configuration externe n'est modifiée par l'implémentation locale. npm exige au minimum CLI `11.5.1` et Node `22.14.0` ; conserver Node 26 du dépôt et sélectionner/épingler à l'implémentation une version npm compatible vérifiée. L'utilisateur a signalé avoir rendu le dépôt public. Nouvelle vérification de l'API GitHub le 15 novembre 2026 : `visibility: public`, `private: false` (métadonnées mises à jour à `17:36:24Z`). Le registre npm public confirme `@acrasie/forgix`, versions stables `1.0.0` et `1.0.1`, `latest: 1.0.1` ; la version historique `0.0.0-stage` n'entre pas dans les releases stables de cette migration. Trusted Publishing OIDC et attestation de provenance sont deux capacités distinctes : npm génère automatiquement cette dernière pour le couple dépôt public/paquet public. Retenir donc OIDC avec provenance automatique obligatoire, sans changer la visibilité dans cette tâche. Revérifier ces préconditions avant activation ; si le dépôt redevient privé, bloquer avant publication et demander une nouvelle décision, sans désactiver silencieusement la preuve. Le contenu actuel des réglages npm et les protections de tags ne sont pas vérifiés par cette conception. Pas de fallback token silencieux. `npm whoami` n'est pas une preuve d'autorisation OIDC.

Sérialiser toutes les opérations de release du dépôt, pas seulement celles d'un tag : `vX.Y.Z` et `npm-vX.Y.Z` pourraient sinon publier la même version. Utiliser `queue: max` et `cancel-in-progress: false`, capacité documentée également employée par le miroir. Jusqu'à 100 runs peuvent attendre ; au-delà, GitHub annule le surplus. L'ordre de dispatch n'est pas garanti. Signaler ces annulations et reprendre explicitement leur tag ; ne pas prétendre garantir une file illimitée sans perte. Un ancien candidat ne doit pas faire régresser le dist-tag npm `latest` : avant une nouvelle publication, exiger une version supérieure à `latest` ; pour une reprise d'une version existante vérifiée, ne pas réécrire `latest`. GitHub `latest` ne doit pas être automatiquement promu par une release plugins seuls ou une reprise ancienne ; l'avancement automatique est limité aux nouvelles releases npm plus récentes vérifiées. La concurrence du miroir reste séparée ; pas de verrou récursif entre appelant et workflow appelé.

## Reprise, migration et rollback

Git, npm, GitHub Releases et miroir ne forment pas une transaction. Le résultat du run expose séparément validation, npm, GitHub et miroir ; un échec miroir ne doit pas être annoncé comme une absence de publication npm.

- Relancer le run original ou dispatcher avec la référence d'exécution du même tag existant et la même entrée tag, avec résolution et validations à nouveau. Le contexte `github.sha` doit encore égaler le SHA source. Le SHA enregistré doit correspondre au tag courant ; un tag déplacé bloque, il ne devient pas une nouvelle release.
- Si npm a accepté la version mais la réponse a été perdue, lire le registre et comparer l'intégrité au tarball validé avant de sauter la publication. Une présence nom/version seule ne suffit pas. Une différence bloque, sans overwrite/unpublish. Sur une nouvelle exécution, reproduire et vérifier le tarball ; une différence de digest exige investigation, pas adoption automatique du paquet distant.
- Si GitHub Release manque après npm, terminer uniquement les étapes manquantes. Si GitHub Release existe, vérifier l'identité et les notes avant de la réutiliser. Si seul le miroir manque, relancer son job ou dispatcher sa version ; ne pas recréer npm ou GitHub Release.
- Une tentative de publier la même version npm par une autre famille de tag bloque, même avec un tarball identique : un seul tag propriétaire par version, enregistré dans les preuves de release et vérifié lors de la réconciliation. Les versions historiques déjà publiées sont inventoriées avant migration ; leur reprise reste un cas de récupération explicitement vérifié, jamais un backfill automatique.
- Avant la bascule, inventorier tags/releases/versions npm distants et releases partielles ; terminer ou documenter les exceptions avant activation. Une PR atomique remplace l'ancienne autorité locale et Release Please par la nouvelle préparation/CI/runbook. Ne jamais laisser deux workflows de publication autoritaires actifs. Configurer et vérifier OIDC et autorisation des tags avant le premier tag nouveau ; ne pas pousser les anciens tags pour tester.
- Avant publication, revenir sur la PR reste possible selon le workflow Git normal. Après publication, correction en avant avec nouvelle version/cachebuster. Ne jamais déplacer un tag, réécrire `main`, réutiliser une version npm ni supprimer automatiquement une release distante. La réactivation de l'ancien outil nécessiterait une décision distincte et sa réconciliation ; ce n'est pas un rollback automatique sûr.

## Preuves attendues

4. 6. Activation ultérieure explicitement autorisée : vérifier réglages trusted publisher, environnement `release` limité aux tags de release protégés et protection des tags, revérifier visibilité publique du dépôt et du paquet avant toute publication, puis première vraie release depuis son SHA approuvé ; lire les résultats CI, intégrité npm, provenance obligatoire, release GitHub et miroir. Pas de publication factice en production. Tant que cette étape n'a pas eu lieu, annoncer publication/OIDC non vérifiés, même si les checks locaux sont verts.
